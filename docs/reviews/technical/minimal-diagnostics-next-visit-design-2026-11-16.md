# Minimal diagnostics and next-visit updates — 2026-11-16

Owner requested technical-only Sentry diagnostics with placeholders for private values. For PWA updates, the owner explicitly rejected pausing/saving work on update: finish the current visit, then offer a button on the next fresh opening. Implementation is local sandbox work, not a release or monitoring activation.

## Diagnostic boundary

Allow only static app/build information, known technical error classes, bundled module/line/column locations and coarse browser/OS/device context needed for diagnosis. Private exception text, identity, notes, song/file names, arbitrary URLs/queries, headers/cookies, request/response bodies, raw user agents, local variables, DOM state and user-generated context are withheld. Use a static placeholder such as “Private data unavailable (withheld for privacy)” rather than claiming a failed retrieval or inventing identifying values.

Use fresh allowlisted events and an error-only transport boundary, not only a denylist in beforeSend. Disable session health reports, replay, tracing/profiling, logs, feedback, attachments, client reports and unknown envelope types. SDK settings and integration selection must be checked against the installed version. The existing SDK is Sentry 11.12.0: v11 dataCollection defaults apply even without opting into that object, and BrowserSession is separate from error-event sanitization. Tests must inspect serialized envelopes using a fake transport, with no vendor requests.

This implements minimization, not a legal compliance certificate. Even a sanitized browser HTTPS request exposes source IP and ordinary HTTP User-Agent/network metadata to its receiver; omitting raw user-agent from the event body does not make the request anonymous. Use credentials omission/no-referrer, but client code cannot eliminate all browser transport metadata or establish how the provider stores/logs it. A relay would be separate backend scope, not part of this work. Vendor data region, retention, DPA, legal basis, transparency and any required consent remain owner decisions before hosted activation. No Sentry project, DSN, upload token or policy change is included. Primary references: [Sentry SDK options](https://docs.sentry.io/platforms/javascript/guides/react/configuration/options/), [BrowserSession](https://docs.sentry.io/platforms/javascript/guides/react/configuration/integrations/browsersession/), [European Commission data-protection principles](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/principles-gdpr_en), [EDPB basics](https://www.edpb.europa.eu/sme/learn-the-basics/data-protection-basics_en).

## PWA-NEXT-VISIT-v2

Only a fresh document boot opens the startup opportunity. Inspect registration.waiting and run one initial update check, including an installing worker's terminal state within a bounded startup window. Offer Update/Later if an update is available before ordinary interaction/navigation. Once the initial check settles without a waiting worker, times out, or the user begins ordinary interaction, this document is active: later discoveries stay hidden. Focus, reconnect, visibility resume and BFCache return do not start another visit. Later suppresses the notice for the rest of this document.

Activation needs an explicit click and current local safety. Do not autosave, pause timers, submit forms or create calendar events for an update. Pristine idle Login may update; typed credentials/registration/recovery fields are unsafe and must never be persisted or submitted by this mechanism. If all old clients closed and the browser already activated the new worker naturally, use the existing release summary; no fake update step.

Use actual same-origin in-scope window clients rather than expiring localStorage heartbeats. A waiting-worker companion inspects clients.matchAll with includeUncontrolled, requires the requesting window to be the only app client, gives a short-lived single-use source-bound approval, then re-enumerates before skipWaiting. Other/suspended/unresponsive app windows block with close-other-windows guidance. Reply only with status/counts, never window URLs or private state. Unknown APIs, stale/replayed grants, missing source, offline state and timeouts fail closed.

Installed vite-plugin-pwa ignores updateSW(false)'s argument and installs an unconditional controlling reload if onNeedReload is omitted. Supply that callback and route it plus native controllerchange through one explicit-consent/idempotent safety gate. Workbox emits configured importScripts before its generated SKIP_WAITING message listener, allowing the companion to intercept the generic message and reserve skipWaiting for the checked protocol. Keep skipWaiting/clientsClaim automatic options off. Verify generated output ordering in one focused build, not merely source tests. Reference: [Vite PWA prompt updates](https://vite-pwa-org.netlify.app/guide/prompt-for-update.html), [Workbox window lifecycle](https://developer.chrome.com/docs/workbox/modules/workbox-window).

This coordinates this app's windows only, not arbitrary tabs or users/devices. No Push API subscription or closed-iOS background delivery is added. A mobile OS may suspend and restore the same document instead of closing it; that remains the same visit and does not create a new prompt. A genuinely fresh load is required for a new offer. Browser-native waiting-worker activation after all clients close and already-running legacy workers limit cross-version guarantees. No absolute atomic global-tab lock/data-loss guarantee is claimed. See [page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) and [pageshow/BFCache restoration](https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event).
