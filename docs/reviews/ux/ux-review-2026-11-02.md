# UX and accessibility review — 2026-11-02

Started 2026-11-02; completed 2026-11-03. Audience: musicians who are new to this app, including both experienced self-directed players and people who need more guidance—not only beginner guitarists.

Guitar Practice Hub has a useful foundation for regular practice: a prominent Practice action, ready-made blocks, timers close to the activity, clear week/date context and a restrained visual style. It does not need a wholesale redesign. The main opportunity is to make the rules obvious to someone who has not watched the app being built: what a block means, which changes have saved, where settings live and how to recover when there is no usable week.

I would improve those everyday interactions before adding more features. Accessibility has several good foundations, but this review is not a WCAG conformance verdict or a substitute for testing with disabled users. The two friends already using the beta are valuable participants: observe what they expect, rather than teaching them the intended gestures first.

## Scope and evidence

Reviewed all seven pages—sign-in/account flows, Home, Progress, Plan, Practice, Stats and Settings—plus navigation, tours, pickers, materials and media controls. App source baseline is `6776bfd` / 0.5.0; the unreleased hosting work does not redesign these screens. The [backlog](../../guitar-hub-v1-scope-and-backlog.md) and [handoff](../../project-handoff.md) remain the status sources; these are recommendations, not approved UX implementation or release scope.

## The six most useful improvements

### UX-01 — Let people enlarge the interface

**Priority: high. Evidence: source-observed zoom policy and browser-observed enlarged-layout problem; physical pinch behavior unverified.**

The viewport explicitly requests `maximum-scale=1.0` and `user-scalable=no` ([index.html](../../../index.html#L7)). A player with low vision, a phone on a stand or tired eyes may need magnification during practice. Modern browsers can override such restrictions, so this setting alone does not establish the exact behavior on every device. It creates a barrier in browsers that honor it.

The browser review found a separate, concrete layout problem under root-font enlargement: at 390px width the tuner's bounding box extended from x=336 to x=416, outside the viewport. Some block names wrapped one character per line and the date heading broke into difficult fragments ([capture](../../evidence/ux/2026-11-03/practice-text200.png)). Global horizontal clipping meant a simple “no horizontal scrollbar” check would miss this loss. This stress case supports fixing enlarged-layout resilience; it does not prove a physical device blocks pinch zoom.

Recommend allowing user scaling, then checking text enlargement and reflow. This reverses an intentional earlier product choice; it needs the owner's decision, not an unannounced edit. Preserve accidental-gesture protection through targeted interaction design rather than disabling page magnification globally.

**Acceptance:** readable/operable at 200% text enlargement and at 320 CSS-pixel width, including the fixed header, calendar, expanded block and Save action; physical-browser pinch zoom works where supported. WCAG AA addresses [text resizing to 200%](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) and [reflow at an equivalent 320 CSS pixels](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); zoom emulation is not proof of every device's behavior.

### UX-02 — Make “what has saved?” obvious

**Priority: high. Evidence: source-observed saving models and browser-observed layout; newcomer confusion is a design hypothesis.**

Plan has a main Save plan action, a separate Save composition action and immediately saved Repertoire associations ([Plan](../../../src/pages/Plan.tsx#L1475), [song status](../../../src/pages/Plan.tsx#L1659), [Save plan](../../../src/pages/Plan.tsx#L1667)). The rendered Plan already explains that song-list changes save immediately; preserve that useful copy. Practice saves its session explicitly, while materials are saved locally and ToDo edits have their own persistence. These are legitimate separate operations; the improvement is making the overall state and scope easy to scan, rather than assuming the app provides no explanation today.

Recommend a small persistent save-state summary for the current task, retaining the existing song-list explanation and making “Plan details: unsaved changes” and “Files stay on this device” easy to find. Keep explicit-save behavior and the existing guards. On long Practice pages, consider a compact save/status bar that remains available without covering content; retain the ordinary in-flow button as an accessible fallback. Do not introduce global autosave as a side effect.

**Acceptance:** after editing focus, changing a song and adding a file, a first-time user can correctly explain which changes are saved, where and whether Save plan affects them. A failed save retains edits and announces the error. The current passing persistence checks are a strength; this recommendation concerns communication, not a new claim of data loss.

### UX-03 — Give keyboard and screen-reader users a clear place to land

**Priority: high. Evidence: source-observed omissions and bounded keyboard/DOM observations.**

The navigation button has a name but no expanded state or control relationship ([Layout](../../../src/components/Layout.tsx#L104)). The shared shell does not set a page-specific document title or move focus to the new page heading, and has no skip-to-main link ([main](../../../src/components/Layout.tsx#L195)). When a menu item disappears after navigation, users need an intentional destination and an indication that the screen changed.

QA confirmed missing expanded/control attributes with the menu both open and closed. After opening the menu, Tab visited Go back, Metronome and Tuner before Home and Progress: it is operable, but the navigation choices are not the immediate next destination. Escape returned focus to the named menu opener, which is useful. Sampled programmatic navigation to Stats kept the generic title “Guitar Practice Hub” and did not focus a new-page heading; focus stayed on the menu opener. Do not interpret that sequence as proof that keyboard navigation fails or that focus always falls onto the document body.

Recommend `aria-expanded`, a stable panel ID, predictable open/close focus, a skip link and a route-heading focus/page-title convention. This is a nonmodal navigation disclosure: it does **not** require a modal focus trap. The existing native picker dialog already offers useful Escape/return-focus behavior and should be retained. W3C's [disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/) describes exposing the expanded state.

Also make repeated controls self-describing: “Mark Chromatic done,” “Start Chromatic timer,” “Remove Chromatic block.” The Done checkbox currently uses only the block name ([Practice](../../../src/pages/Sessions.tsx#L2335)); repeated removal actions share one generic name ([remove](../../../src/pages/Sessions.tsx#L2360)). Plan calendar days should expose full dates and relevant selection/week state rather than only a number.

**Acceptance:** keyboard-only Home → menu → Plan → Practice → picker → close works with visible focus, no lost focus and a clear new-page location. A screen-reader user can identify the affected block and selected date without relying on spatial position. Existing large surrounding checkbox labels count as the target; do not mistake the small check glyph for the full hit area.

### UX-04 — Give empty and failed states a truthful next step

**Priority: high for an affected user. Evidence: source-observed and deliberately empty-fixture browser observations; frequency is not known.**

Progress says “Start a program from Plan” ([Progress](../../../src/pages/Progress.tsx#L298)), while Plan exposes week/composition controls rather than an obvious Start program button. Plan can display the internal term `plan_weeks` ([Plan](../../../src/pages/Plan.tsx#L1383)). Home converts a failed load into no-week state, and can label the first scheduled historical week “Current Week” when none covers today ([Home load](../../../src/pages/Landing.tsx#L42), [fallback](../../../src/pages/Landing.tsx#L49)).

The deliberately empty browser fixture reproduced the Progress instruction and Plan's “No plan_weeks row covers today's date” message, without a corresponding Start program control. Empty Practice instead offered an honest Add block state. Home's failed-load/historical-week behavior remains a source finding; no live failure or ordinary-signup failure was reproduced.

Recommend distinguishing “Couldn't load your plan—Retry” from “You have no week for today.” Label a historical selection honestly. Replace database terminology with plain language and point to an existing, valid recovery action. The no-week recovery flow itself is already an open product decision; do not invent a new Default-program creation feature during copy cleanup.

**Acceptance:** failed request, truly empty account and history with no current week produce different messages; every suggested button/action actually exists and leads somewhere useful. Existing scheduled data is preserved.

### UX-05 — Make ordinary settings discoverable without a secret gesture

**Priority: medium. Evidence: source-observed gesture, browser-observed keyboard access; discoverability is a design hypothesis.**

Metronome settings require a hold, right-click or Shift+Enter; a normal tap starts/stops sound ([handlers](../../../src/pages/Sessions.tsx#L1348), [control](../../../src/pages/Sessions.tsx#L1913)). The tour explains this, but a returning user who skipped it has little visible evidence. The playing control's accessible name becomes simply “Playing,” losing the tool's identity.

QA confirmed that Shift+Enter opens the settings. This is a discoverability problem to test with a newcomer, not a claim that there is no working keyboard path.

Recommend a visible settings affordance or labelled adjacent control while preserving quick play/stop. Use action names such as “Stop metronome” and “Metronome settings.” Do not remove existing shortcuts. Make the reference-tone-only nature of the tuner clear so a beginner does not expect microphone pitch detection.

**Acceptance:** a friend who has not seen the tour can change BPM and volume without being told to hold the icon. Play/stop remains quick, keyboard-operable and independent of settings.

### UX-06 — Explain the practice workflow at the point of use

**Priority: medium. Evidence: design hypothesis supported by source layout.**

The useful building blocks are present, but terms such as block, composition, program, week focus and ToDo assume a learned mental model. The checkbox next to an activity can look like selection rather than completion. Advanced material/loop controls make an expanded block much longer even when a player only wants to time an exercise ([Practice block](../../../src/pages/Sessions.tsx#L2330), [media controls](../../../src/components/VideoPracticeControls.tsx#L93)).

Recommend a brief contextual cue—“A block is one activity. Start its timer or enter time; mark Done if completed, then save the session”—with a visible Done label/legend. Explain that Done records completion rather than inventing minutes: a Done-only zero-minute block can be saved, while the practiced-day calendar uses positive saved minutes. Preserve those accepted rules; clarify them instead of treating the difference as a new data bug. Keep advanced media controls available, but consider a compact basic player plus an expandable Loop/bookmark section. Continue progressive disclosure rather than introducing a mandatory setup wizard or prescribing a curriculum.

**Acceptance:** a newcomer completes one five-minute activity, understands the Done checkbox and finds Save without coaching. An experienced user can still start practice quickly. Optional supplied guidance and the existing per-screen Help remain available; essential workflow cues should not live only in a long tour.

## Accessibility strengths and limits

Keep the common roughly 44px controls, visible focus outlines, native labels/buttons, source-implemented native-picker focus restoration, category keyboard support, reduced-motion picker behavior, translated interfaces and runtime document-language updates. In the sampled Help tour, Tab cycled between Close and Next and Escape closed it. Return focus after the tour was not verified because the test's programmatic activation did not focus Help first. The chart's data table and non-color category labels are stronger than a chart-only presentation.

Do not claim that every control must be 44px to meet AA: WCAG 2.2's [minimum target criterion](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) uses 24×24 CSS pixels with defined spacing/equivalent-control exceptions; 44px is a useful ergonomic goal for an instrument-in-hand app. No complete contrast measurement, screen-reader audit or physical-device conformance test was completed. The horizontally scrollable practice-day strip is intentional and was not classified as a layout defect. The minor enlarged-Plan boundary overrun was not promoted into an unsupported severe accessibility finding.

## Suggested sequence and beta-user tasks

My proposed first batch is deliberately small:

| Batch | Change | Why first |
| --- | --- | --- |
| A — Accessibility and orientation | Fix enlarged-text header and block-name reflow, revisit zoom restriction, add navigation expanded state/skip link and a consistent new-page focus/title, name Done/timer controls in context. | Addresses the observed clipping/wrapping and removes navigation barriers without changing the practice model. Zoom policy still needs an explicit owner decision because it reverses an earlier choice. |
| B — Confidence while saving | Explain Plan's independent save scopes and device-local files; keep current persistence and error guards. | A user should know what has saved before leaving, rather than learn the rules through trial and error. |
| C — Truthful recovery | Replace internal/no-week instructions with plain-language states and an action that actually exists; distinguish load failure. | Stops an affected user reaching a dead end. Any new program-creation/recovery feature needs its own agreed scope. |

Then address metronome discoverability and the short block/Done explanation. Treat the remaining table as refinements, not a demand to rebuild every screen. These are proposed work packages for selection; no UX implementation is approved or added to the next release automatically.

For the two beta users, choose three of these for a short session; give tasks without naming the intended control:

1. “Log five minutes of practice for today, then show me how you know it saved.”
2. “Add a song to this week. What do you think Save plan saves?”
3. “Change the metronome speed.”
4. “Find what you practiced last month, then return to today.”
5. “Add a reference file. Would you expect it on another device?”
6. “After skipping Help, explain the difference between Plan, Progress and Practice.”

Watch where they pause, backtrack or expect a different result. Ask what they expect before explaining anything. Two friends can reveal confusing assumptions, but they cannot establish accessibility across disabilities or prove that an issue affects most users.
